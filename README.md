# cli-llm-bridge

A small local server that speaks both the **OpenAI Chat Completions API** and the
**Anthropic Messages API**, and answers every request by running your own, unmodified
[Claude Code](https://code.claude.com/docs) CLI in headless mode (`claude -p`).

Any application that lets you set an OpenAI or Anthropic base URL (the official SDKs,
LangChain, LiteLLM, many agent frameworks) can then use the Claude account you are already
signed in to in Claude Code.

## Limitations

Know these before you connect an application. The bridge imitates two APIs on top of a
command-line tool, so it is not a full replacement for either.

**Speed and streaming**

- **Every request takes several seconds**, even for a one-word answer, because each one starts
  a new `claude` process. Tool calling and structured output add a little more. Applications
  that make many calls (agent frameworks often make dozens per task) will be noticeably
  slower than with a real API.
- **Streaming is not real-time.** `stream: true` works, but the whole answer arrives in one piece
  when it is finished. Applications that show text as it is typed will show nothing, then
  everything.
- **Parallel requests are capped** by `--max-concurrency` (default 2). Extra requests wait in line.

**Content and parameters**

- **Text only.** Images, documents, PDFs and audio are rejected with HTTP 400.
- **Sampling and length settings are ignored**: `temperature`, `top_p`, `top_k`, `seed`,
  `max_tokens`, `stop` / `stop_sequences`, `n`, `logprobs`, presence and frequency penalties.
  Answers can be longer than `max_tokens`, and you always get exactly one answer.
- **Multi-turn conversations are sent as a labelled transcript** inside one prompt, not as real
  separate turns. Models handle this well, but it is not identical to the real API.
- **Token counts are approximate.** They come from Claude Code and include the bridge's own
  instructions (for example, the tool descriptions), so they differ from what the real API
  would report for the same request.

**Tool calling and structured output**

- **Tool calling is emulated**, not native: the model is asked to return its tool calls as
  structured output, which the bridge converts into the API's tool-call format. It works with
  the official SDKs and LangChain and passed every test run, but it is not guaranteed to be as
  reliable as the real API, especially with smaller models such as Haiku.
- **Tool-call IDs are generated by the bridge** and do not follow either provider's ID format.
- **OpenAI:** the legacy `functions` / `function_call` parameters are not supported; use `tools`.
- **Anthropic:** only client tools you run yourself are supported. Server tools (web search,
  web fetch, code execution, computer use, text editor and so on) are rejected with HTTP 400.

**Endpoints that do not exist**

- **OpenAI:** only Chat Completions. No Responses API, legacy Completions, embeddings, images,
  audio, moderation, files or batches.
- **Anthropic:** only Messages. No token counting (`/v1/messages/count_tokens`), Batches or
  Files API. Extended thinking is not returned, and prompt caching (`cache_control`) and
  citations are ignored.
- **`GET /v1/models` returns a fixed list** of aliases (`sonnet`, `opus`, `haiku`, `fable`).
  Other model names your Claude Code version accepts still work in requests.

**Accounts and limits**

- **Every request counts against your plan's usage limits**, the same as using Claude Code
  yourself. When you reach a limit, requests fail with the error Claude Code reports.
- **The bridge has no authentication.** It accepts any API key. That is why it listens only on
  `127.0.0.1` by default.

**Platforms**

- The bridge uses only the Python standard library and is written to run on Windows, macOS and
  Linux. So far it has been tested on Windows with Claude Code's native installer. Reports from
  other systems, and from Windows installs made with npm, are welcome.

## Privacy and security

- **Your requests go to Anthropic, through Claude Code, and nowhere else.** The bridge makes no
  other network connections.
- **No credentials are touched.** The bridge never reads, stores, or forwards your login, tokens
  or API keys. It only starts the `claude` executable, which handles sign-in itself.
- **Nothing is logged or kept.** The bridge prints one line per request to the terminal (client
  address, time, method, path and status) and never logs prompt or response content. Each
  request runs in a fresh temporary folder that is deleted afterwards. Sessions are not saved
  (`--no-session-persistence`).
- **Your local setup stays out of requests.** Claude Code runs with `--safe-mode`, so your
  CLAUDE.md files, hooks, plugins, skills and MCP servers are not loaded into the conversation.
- **The model cannot touch your machine.** All built-in Claude Code tools are disabled
  (`--tools ""`), so the model cannot read files or run commands. Tool calls requested by your
  application are returned to your application, which runs them as usual.
- **Local only by default.** The server listens on `127.0.0.1`. Binding to another address
  makes your account usable by anyone who can reach the port. The server prints a warning if
  you do this.

## Requirements

- Python 3.10 or newer. There are no other Python dependencies.
- [Claude Code](https://code.claude.com/docs/en/quickstart), installed and signed in. Check that
  `claude -p "hello"` works in a terminal before starting the bridge.
- Windows, macOS or Linux.

## Installation

### With pip

```bash
git clone https://github.com/tomaszkubiak-courses/cli-llm-bridge.git
cd cli-llm-bridge
python -m venv .venv
```

Activate the virtual environment:

```bash
# macOS and Linux
source .venv/bin/activate
# Windows (PowerShell)
.venv\Scripts\Activate.ps1
# Windows (cmd)
.venv\Scripts\activate.bat
```

Then install:

```bash
pip install .
```

### With uv

```bash
git clone https://github.com/tomaszkubiak-courses/cli-llm-bridge.git
cd cli-llm-bridge
uv sync
```

Or install it as a standalone command, available everywhere:

```bash
uv tool install .
```

### Without installing

The bridge is a single file with no dependencies, so this also works:

```bash
python cli_llm_bridge.py
```

## Running

```bash
# pip install (inside the activated virtual environment) or uv tool install
cli-llm-bridge

# uv project environment
uv run cli-llm-bridge
```

The server prints both base URLs, by default:

```text
OpenAI base URL:    http://127.0.0.1:8765/v1
Anthropic base URL: http://127.0.0.1:8765
```

Stop it with Ctrl+C.

Options:

| Option | Default | Meaning |
| --- | --- | --- |
| `--host` | `127.0.0.1` | Address to listen on. Keep it local. |
| `--port` | `8765` | Port to listen on. |
| `--claude` | found on `PATH` | Path to the `claude` executable. |
| `--default-model` | CLI default | Model used when a request names none (or names `default`). |
| `--max-concurrency` | `2` | Maximum number of `claude` processes running at once. Extra requests wait. |
| `--timeout` | `600` | Seconds to wait for one answer. |

## Connecting an application

Both APIs are served at the same time; there is nothing to switch. The bridge tells them apart
by the path the client calls: OpenAI clients call `/v1/chat/completions`, Anthropic clients
call `/v1/messages`. Pick whichever provider your application supports and point it at the
matching base URL. If it supports both, either works: they end up as the same prompt to
Claude Code.

The API key can be any non-empty string. The bridge ignores it, but most clients refuse to
start without one.

### As an OpenAI-compatible provider

Base URL: `http://127.0.0.1:8765/v1`

```bash
curl http://127.0.0.1:8765/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "sonnet", "messages": [{"role": "user", "content": "Hello!"}]}'
```

```python
from openai import OpenAI

client = OpenAI(base_url="http://127.0.0.1:8765/v1", api_key="unused")
reply = client.chat.completions.create(
    model="sonnet",
    messages=[{"role": "user", "content": "Hello!"}],
)
print(reply.choices[0].message.content)
```

```python
from langchain_openai import ChatOpenAI

llm = ChatOpenAI(model="sonnet", base_url="http://127.0.0.1:8765/v1", api_key="unused")
```

### As an Anthropic-compatible provider

Base URL: `http://127.0.0.1:8765` (no `/v1`: Anthropic clients add it themselves)

```bash
curl http://127.0.0.1:8765/v1/messages \
  -H "Content-Type: application/json" \
  -d '{"model": "sonnet", "max_tokens": 1024, "messages": [{"role": "user", "content": "Hello!"}]}'
```

```python
import anthropic

client = anthropic.Anthropic(base_url="http://127.0.0.1:8765", api_key="unused")
reply = client.messages.create(
    model="sonnet",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Hello!"}],
)
print(reply.content[0].text)
```

```python
from langchain_anthropic import ChatAnthropic

llm = ChatAnthropic(model="sonnet", base_url="http://127.0.0.1:8765", api_key="unused")
```

### Environment variables

Many tools read their provider settings from environment variables: `OPENAI_BASE_URL` (or
`OPENAI_API_BASE`) and `OPENAI_API_KEY`, or `ANTHROPIC_BASE_URL` and `ANTHROPIC_API_KEY`.

**Set the Anthropic variables only for the application, never for the bridge or system-wide.**
Claude Code reads the same variables:

- An `ANTHROPIC_API_KEY` placeholder such as `unused` would make Claude Code try to sign in with
  that fake key, and every request would fail.
- An `ANTHROPIC_BASE_URL` pointing at the bridge would make Claude Code call the bridge instead
  of Anthropic. The bridge removes that one variable before starting `claude`, but keeping it
  out of the bridge's environment is cleaner.

### Models

The `model` field is passed to `claude --model`, so it accepts whatever your Claude Code
version accepts: aliases such as `sonnet`, `opus`, `haiku` and `fable`, or full model names.

## What is supported

| Feature | OpenAI API | Anthropic API |
| --- | --- | --- |
| Endpoint | `POST /v1/chat/completions` | `POST /v1/messages` |
| Model list | `GET /v1/models` | `GET /v1/models` |
| Messages | system, developer, user, assistant, tool | `system`, user, assistant |
| Tool calling | `tools`, `tool_choice` (emulated) | `tools`, `tool_choice`, `tool_use`, `tool_result` (emulated) |
| Structured output | `response_format` (`json_schema`, `json_object`) | `output_config.format` (`json_schema`) |
| Effort | `reasoning_effort` | `output_config.effort` |
| Streaming | yes, one chunk at the end | yes, one delta per block at the end |
| Images and documents | no (HTTP 400) | no (HTTP 400) |

See [Limitations](#limitations) for everything else.

## How it works

Chat APIs are stateless: the client sends the whole conversation with every request. The
bridge keeps that model. For each request it:

1. Translates an Anthropic request into the OpenAI shape, if needed, so both APIs share one
   code path.
2. Takes the system messages as the system prompt and the remaining messages as the prompt.
   A single user message is sent as is; longer conversations are sent as a labelled
   transcript.
3. Starts a fresh `claude -p` process in an empty temporary folder, sends the prompt on
   standard input, and waits for the JSON result.
4. Converts the result into a response in the format the client asked for and deletes the
   temporary folder.

**Tool calling** is emulated with Claude Code's structured output (`--json-schema`). The reply
is constrained to `{"content": ..., "tool_calls": [...]}`, where each tool call must match the
name and parameter schema of one of the tools in the request. The bridge turns that into a
standard tool-call response, your application runs the tools, and sends the results back in
the next request, exactly as with a real provider.

## Using an API key

Claude Code uses the `ANTHROPIC_API_KEY` environment variable when it is set, and the bridge
passes its environment to `claude`. Start the bridge with a real API key in that variable and
all requests are billed to the key under Anthropic's Commercial Terms instead of using your
subscription. Unset it if you meant to use your subscription.
